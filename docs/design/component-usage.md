# Component usage guide

Use the existing component's public API and its owning feature's behavior. [Recipes](components.md) record the current defaults; [foundations](foundations.md) describe the visual roles. The examples below are decisions for new compositions, not claims that every existing screen already follows them.

## Choose the surface

| Need | Correct | Incorrect | API / boundary |
| --- | --- | --- | --- |
| A bounded task that interrupts the current view | Open a named dialog for a new post or a clear destructive confirmation; provide Cancel and a specific completion action | Put ordinary destination navigation or an entire settings hierarchy inside repeated nested dialogs | [Modal](../../apps/web/src/shared/ui/Modal.tsx): `onClose`, render-prop `children(requestClose)`, optional `aria-label` / `aria-labelledby` / `aria-describedby`; use `requestClose` for its closing animation |
| A detail/settings journey with its own Back | Use a titled panel; keep Back available and route changes explicit | Use a tiny menu for multiple input fields or rely on outside click as the only way back | [SlideOverPanel](../../apps/web/src/shared/ui/SlideOverPanel.tsx): `title`, `onClose`, `children`, `headerRight`; host-aware placement. Its API does not promise modal focus containment; decide modal semantics at the composition boundary |
| Short contextual actions on an item | Put Save / View profile in an overflow menu; keep the screen's main action visible | Hide Send / Follow / Submit as a menu-only action, or embed a form in a menu | [DropdownMenu](../../apps/web/src/shared/ui/DropdownMenu.tsx): `items`, `onClose`, `align`, `aria-label`; items use stable `key`, `label`, `onClick`, optional `danger`, `checked`, `submenuItems` |
| Explain a nonessential icon | Give the action an accessible name and provide tooltip text on hover/focus | Put required error recovery or the only explanation of a touch action inside a tooltip | [Tooltip](../../apps/web/src/shared/ui/Tooltip.tsx); essential information also appears as visible text |
| Navigate to another destination | Use route navigation or an explicit panel Back while preserving the draft | Treat navigation as a destructive confirmation or clear text whenever a destination changes | [Application shell](../../apps/web/src/app/App.tsx), [prototype flow](prototypes.md#flow-and-actions) |

Modal supplies named dialog semantics, focus containment/return and topmost Escape handling. Give a dialog a meaningful heading or explicit accessible name. A settings panel is a different primitive: do not infer focus trapping, scroll locking or dialog semantics merely from a full-screen surface. Menus expose commands, not a new route hierarchy. Inspect the owning screen for stacking, scroll reservations and unsaved-content policy before adding any overlay.

## Prioritize actions and feedback

| Situation | Correct | Incorrect | Existing implementation |
| --- | --- | --- | --- |
| One main form action | Use one primary action, e.g. **Save changes**; secondary **Cancel**. Reuse feature-specific Send/Follow appearance where applicable | Make every button primary, or replace the outgoing-message gradient with generic white solely because shared Button defaults to white | [Button](../../apps/web/src/shared/ui/Button.tsx): `variant="primary" / "secondary"`, `loading`, native button props; [MessageComposer](../../apps/web/src/features/chat/ui/MessageComposer.tsx), [FollowButton](../../apps/web/src/features/follow/ui/FollowButton.tsx) |
| Pending submission | Preserve the task context, show pending feedback, prevent duplicate activation and keep an accessible loading announcement | Allow another submit while the first is pending or signal progress only through a color change | Button's `loading` forces disabled and exposes `aria-busy`; callers still own submission state and repeated-request handling |
| Invalid input | Show actionable field text such as **Enter a valid email address**, keep the value, and associate the message with the input | Show only a red border, clear all fields, or use placeholder text as the only label | [Input](../../apps/web/src/shared/ui/Input.tsx): `label`, `error`, `rightElement`, native/ref props; errors set `aria-invalid` and merge IDs into `aria-describedby` |
| Failed loading | Keep useful content/drafts when possible; explain the failure and provide **Retry** for the failed operation | Render **No posts yet** after a failed request or display a success notice without a successful operation | Owning query state plus [state inventory](components.md#state-inventory-for-reuse); the HTML [failure presets](prototypes.md#state-and-accessibility-checks) are proposals |
| Offline status | Show connection status accessibly and keep recovery reachable | Assert that all displayed content is cached merely because the browser reports offline | [OfflineBanner](../../apps/web/src/shared/ui/OfflineBanner.tsx) refetches queries on Retry; cache/offline correctness remains the owning feature's responsibility |
| Failed message | Preserve text and the failed bubble; retry that message with visible sending/result state | Lose the draft or produce a duplicate message by creating a new operation blindly on each retry | [Composer](../../apps/web/src/features/chat/ui/MessageComposer.tsx) and owning send/cache logic; the prototype retry is local and does not implement idempotency |
| Empty content | Explain what is missing and provide a useful next action when available | Display skeletons indefinitely or mix empty, unavailable and failed states | [EmptyState](../../apps/web/src/shared/ui/EmptyState.tsx); `SkeletonBone` represents loading, not empty content |
| Destructive action | Use clear destructive wording and `danger` styling; confirm irreversible loss or provide the existing undo mechanism where appropriate | Give Delete the main positive-action treatment, require confirmations for harmless toggles, or promise undo that cannot restore data | DropdownMenu `danger`; [UndoHideSnackbar](../../apps/web/src/features/posts/ui/UndoHideSnackbar.tsx), [UndoClearHistorySnackbar](../../apps/web/src/features/chat/ui/UndoClearHistorySnackbar.tsx) |

Validation explains whether input is acceptable; it does not grant authorization. Server permissions still govern mutations. Pending/disabled controls do not establish idempotency, and a retry action must respect the existing API and cache contracts. Do not log drafts, authentication data or private message text while diagnosing these states.

## Compose and verify

Keep visible labels for essential mobile actions, accessible names on icon-only controls, and focus indication alongside pointer feedback. Use the existing keyboard contracts instead of clickable `div` substitutes. On narrow layouts, allow labels to wrap or scroll rather than clipping them. Keep the composer above the keyboard, account for safe areas and player reservations, and make every dismissed surface restore a meaningful focus position.

Before handoff, exercise default/selected/pending/disabled, loading/empty/failure/retry, long text, narrow/wide layout and keyboard dismissal. Check nested overlays and menus together. [Reference scenarios](scenarios.md) cover the shared web primitives; [mobile/desktop prototypes](prototypes.md) demonstrate proposed adaptation. Neither validates native accessibility or production retry behavior by itself.
