# Screen scenarios and responsive acceptance

This matrix is the implementation/review contract for extending a screen. It distinguishes expected behavior from existing test coverage. The component reference and source inventory define visual recipes; these scenarios define how those recipes should work under different conditions.

## Shared behavior

Additional executable feature coverage and limits are recorded in [extended screens](extended-screens.md). The separate [platform matrix](platform-validation.md) checks Firefox/WebKit and iPhone viewport emulation without treating emulation as physical-device evidence. [Theme readability](theme-readability.md) and [effect performance](visual-performance.md) cover customization and its explicit fallback.

At 320px, 390px, 768px and 1280px widths, verify the affected route with real-length text and keyboard/pointer input. At 200% root text size, controls should wrap, labels/errors remain legible and the page should not require horizontal scrolling; media/code/table content may have its own intentional scroll region. Browser zoom and root text scaling are separate checks. Native clients must also test safe areas and the onscreen keyboard.

Loading should retain the expected layout using appropriately sized placeholders and an accessible status. A failed request should expose retry and preserve user drafts. Empty data is a successful result with no content and should have a meaningful next step. Disabled or pending actions must explain their state through text or semantics where needed. Avoid using hover as the only route to an action on touch devices.

Some of these states still need feature-specific implementation or tests. Reel comment loading/error/empty and retry are now implemented and covered by the extended suite, while upload/send/permission states remain separate feature work. This matrix sets acceptance criteria; it does not certify every current route. Broad feature redesign is not required to reuse the foundations.

## Executable reference coverage

### Continuous actions in the real app

[Interaction regressions](../../apps/web/e2e/design/interactions.spec.ts) exercise the actual React routes with fictional offline API responses at 1280 × 900 and 390 × 844. They hold mutation responses to check optimistic Like/Unlike, Repost/Undo and Save/Remove on Feed and Profile, then verify the refetched state, counts, scroll position and Feed text draft. Pointer activation covers selection; keyboard Space activation also checks retained focus. WebKit pointer activation follows native browser focus behavior. Browser Back from a fully mounted Profile checks Feed draft and scroll restoration.

Chat history uses successive real wheel inputs on desktop; Firefox can limit a single input to less than one viewport. Mobile WebKit does not support Playwright wheel input, so its fixture uses PageUp in the named, keyboard-focusable Message history region. This checks keyboard scrolling, not a native touch swipe. Chat checks cover successful HTTP fallback with a held acknowledgement, failed send and Retry with the same client message identity/sequence, preservation of a newer draft, composer focus and history position. A timer-controlled narrow-screen Back checks the last input before the reply-state debounce, history restoration and keyboard reopening from the focused conversation row. The [platform configuration](../../apps/web/playwright.platforms.config.ts) runs these assertions alongside browser reflow checks; [validation results](platform-validation.md) distinguish the latest passing evidence from pending checks.

Retention has explicit boundaries: Feed preserves **text in session memory**, not files/polls or page reloads. Chat retains text through its existing draft store, and caches only the last 20 conversation scroll snapshots in memory. Both caches and route positions clear on account/session reset. Browser Back/Forward restores saved window positions while content becomes ready; new navigation starts at the top and explicit anchors keep their existing behavior. Route restoration is bounded to five seconds and user scroll input cancels it.

These fixture tests do not establish production delivery guarantees, encrypted peer compatibility, native keyboard behavior or native screen-reader parity. Follow, collections, overlays and other feature journeys retain their separately listed unit/reference coverage.

`Design/Reference` in Storybook uses the actual shared Button, Input, GlassCard, Avatar, Toggle, RadioGroup, ProfileTabs, Modal, Tooltip and DropdownMenu. It provides Controls, Pending, Empty, Failure, Narrow, LargeText and Tokens stories. The text-size toolbar offers 100/150/200%; viewport presets include phone, narrow phone, tablet and desktop.

`pnpm --dir apps/web test:design` opens built Storybook and the production app bundle through Vite preview on ports 6006/6007. It blocks external requests, compares component screenshots, checks keyboard focus/dismissal/selection, and exercises actual Feed/Profile/Chat with offline API fixtures. Content uses 1280×900/100%, 390×844/100%, and 320×740/200%; empty/error states are separate. Feed/Chat retry preserves drafts, mobile Messenger returns to its list, and enlarged mobile navigation keeps Create actions reachable. Font samples and offline prototypes run in the same suite. See [screen captures](screen-captures.md) and [readability audit](readability.md).

Feed/Profile content captures use full-page screenshots so enlarged composers/profile headers do not hide the post under review. Messenger uses its real viewport and asserts the input has usable width and Send remains inside it. Contrast reports accompany the content tests. These scenarios still do not cover every feature screen in this matrix or native apps.

The checked-in canonical baselines use Chromium on Windows, with platform suffixes. The CI job uses `windows-2025`. Font/OS/browser changes can alter output; review the report and each changed screenshot before accepting a baseline update. A successful local comparison does not prove the hosted runner renders identically. Other platforms require separately reviewed baselines, never automatic baseline generation in CI.

```powershell
$env:VITE_API_URL = 'http://127.0.0.1:3000'
pnpm --dir apps/web build
pnpm --dir apps/web build:storybook --disable-telemetry
pnpm --dir apps/web exec playwright install chromium
pnpm --dir apps/web test:design
# Deliberate local baseline updates after visual review:
pnpm --dir apps/web test:design --update-snapshots
```

The ordinary Playwright route suite excludes `e2e/design`; design tests use their own config/servers. Keep live services and secrets out of visual fixtures. CI uploads failure reports/diffs and never publishes Storybook or sends screenshots to an external service. Build the app before the suite with `VITE_API_URL=http://127.0.0.1:3000` (CI sets this explicitly; the snippet above is PowerShell). On POSIX shells, export the same environment variable before building. Preview serves the production bundle; after source edits rebuild it before rerunning. These offline checks do not replace production API, encryption or native-device verification.
