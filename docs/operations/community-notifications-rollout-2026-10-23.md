# Community notifications rollout — 23 October 2026

Status: production rollout and two-account notification UI acceptance complete.

## Behavior and compatibility

Active members edit only their own server/channel notification preferences. Server mode is ALL, MENTIONS or NONE; a nullable channel override inherits the server mode. Temporary server mute and existing conversation message mute independently suppress alerts until expiry. Calls retain existing mute controls. Message delivery and canonical unread projection do not depend on alert preferences.

Mentions carry at most 50 explicit participant IDs validated inside the authorized message transaction. IDs persist in history, outbox and replay; idempotent retry returns the original message. Forwarded messages start without mentions. Encrypted offline retry reuses its persisted envelope and IDs; losing that envelope cannot silently send the optimistic plaintext. The feature controls existing in-app toasts and sound. The existing offline worker remains a log-only path, so external push delivery is not claimed.

The additive `20261022220000_community_notification_preferences` migration adds the notification enum, server member preferences, nullable conversation overrides and a default-empty message mention array. Older clients keep reading additive responses and default to their previous behavior. Apply the migration through Core before publishing new Messenger handlers or the web client. Do not drop these additive columns during rollback. Older web clients cannot honor the new preference modes until updated.

Personal COMMUNITY_CHANGED events trigger reconciliation without changing the administrator channel revision. Reconnect/resync resets verified preference generations so an inactive cached ALL detail cannot override a newer NONE or mute. Alert delivery waits for current detail and suppresses alerts if it cannot load it. Channel badges use the same unread projection as conversation/global counts, including unloaded pages.

## Release hardening follow-up

Hosted CI run `39960883825` on `7576dbf19e65b7ac14fc0393562051381653ed8f` completed successfully. This is evidence for that revision, not the subsequent hardening changes below. PR #135 remains draft; contribution terms and human approval remain outstanding. Production is still backend `5034d7d6` and frontend `a20a1e7a`.

Further review reproduced two asynchronous boundary defects. Message/reaction alerts could use an outdated active conversation or notification settings after loading conversation preferences. Deferred previews could also expose a name or text after the user disabled that preview field. Delivery now reads current settings and focus before sound/toast effects, and checks preview visibility again after formatting. Regression tests cover opening the chat, disabling notifications, DND, muted actors and hiding names/text during asynchronous work. Message delivery and unread behavior are retained.

An independent reviewer reproduced a public upload completing after channel access changed during staging validation. The existing message transaction already rejects attaching public media to a private channel, so this was not a demonstrated disclosure of private history. Final chat object promotion now holds a shared lock on the owning community, rechecks authorization/privacy through the same Prisma transaction, and waits for bounded S3 publication before releasing the lock. This follows the administrator mutation's community-first lock order. Staging HEAD/decode stay outside the transaction; external storage effects are not retried by the transaction. A 20-second transaction and a storage abort deadline of at most 15 seconds leave headroom for lock release. This serializes normal publication with access changes; it is not a distributed PostgreSQL/S3 transaction, and aborting an S3 request does not prove that a remote copy was rolled back. Slow publication can make a concurrent administrator operation time out and require retry.
